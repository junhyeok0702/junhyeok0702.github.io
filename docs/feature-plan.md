# 기능 계획: 다음 그림 주제 고르기

## 한 줄 요약

내 홈페이지는 내 그림을 소개하는 곳이다. 방문자는 다음에 보고 싶은 그림 주제를 고른다. 서버에는 주제와 선택 시각을 저장한다. 화면에는 주제별 반응 횟수가 보인다. 친구 휴대폰에서도 같은 결과를 보고 재배포 후 유지되면 완성이다.

| 항목 | 결정 |
|------|------|
| 기능 이름 | 다음 그림 주제 고르기 |
| 사용자 행동 | 주제 버튼 하나를 누른다 (자유 입력 없음, 로그인 없음) |
| 저장 데이터 | 주제(`topic`), 선택 시각(`created_at`) |
| 배포 서비스 | Netlify |
| 저장소 | Supabase (`votes` 테이블, `vote_counts` 뷰) |
| 주제 목록 | 풍경 / 인물 / 정물 / 추상 |

## 화면

`index.html`에 섹션 하나를 추가한다 (관심사와 기록 사이).

- **입력:** 주제 버튼 4개. 글자를 입력하는 칸은 없다.
- **버튼:** 누르면 그 주제로 1건 저장한다. 저장하는 동안 버튼을 비활성화한다.
- **결과:** 주제마다 누적 횟수와 비율 막대를 보여준다. 페이지를 열 때 불러오고, 저장 후 다시 불러온다.
- **상태 메시지:** 기존 연락 섹션의 `#toast`와 같은 방식으로 한 줄 표시.

## 성공 · 실패 동작

| 상황 | 화면 동작 | API 응답 |
|------|-----------|----------|
| 횟수 불러오기 성공 | 주제별 숫자 표시 | `GET /api/votes` → 200 `{counts}` |
| 횟수 불러오기 실패 | "반응 수를 불러오지 못했습니다." 숫자는 "—" | 502 또는 500 |
| 저장 성공 | "기록했습니다." 후 숫자 다시 불러오기 | `POST /api/votes` → 201 |
| 허용 목록에 없는 주제 | 저장하지 않음 | 400 |
| DB·네트워크 오류 | "기록하지 못했어요. 잠시 후 다시 시도해 주세요." 숫자 그대로 | 502 |
| 서버 환경 변수 없음 | 위와 같은 실패 메시지 | 500 |

## 구조

```
index.html                    공개 홈페이지 (GitHub Pages도 그대로 사용)
scripts/build.mjs             허용 파일만 dist/ 로 복사하고 검사 (npm 불필요)
dist/                         Netlify 공개 출력 (git 제외, 빌드 때 생성)
netlify.toml                  build·publish·functions 경로
netlify/functions/votes.mjs   /api/votes 서버 함수 (dist/ 로 복사하지 않음)
supabase/schema.sql           테이블·뷰·RLS (Supabase SQL Editor에서 실행)
```

흐름: 브라우저 → `/api/votes` (Netlify Function) → Supabase REST API.
브라우저에는 Supabase 키가 없다. 키는 Netlify 환경 변수에만 둔다.

## 접근 제한

- 로그인 없이 누구나 쓸 수 있는 기능이라 저장 값을 좁게 제한한다.
- 함수는 주제를 허용 목록으로 먼저 검사한다. DB도 `check` 조건과 RLS로 한 번 더 막는다.
- 함수가 쓰는 키는 publishable 키다. secret 키(전체 권한)는 쓰지 않는다.
- `anon` 역할 권한: `votes` 읽기, `topic` 컬럼만 쓰기. 수정·삭제는 불가.
- IP나 기기 정보는 저장하지 않는다.
- 남는 한계: 한 사람이 여러 번 누르는 것은 막지 못한다. 최소 버전에서는 받아들인다.

## 완성 검사 방법

1. **빌드:** `node scripts/build.mjs` 가 "빌드 검사 통과"를 출력하고, `dist/`에 `index.html`과 공개 파일만 있다.
2. **배포:** Netlify 배포 로그가 성공이고, Functions 목록에 `votes` 가 있다.
3. **API:** 배포 주소의 `/api/votes` 를 브라우저로 열면 `{"counts":{...}}` 가 보인다.
4. **저장:** 내 PC에서 주제 하나를 누르면 숫자가 1 오른다. Supabase Table Editor의 `votes`에 주제와 시각이 있는 행이 생긴다.
5. **다른 기기:** 친구 휴대폰에서 같은 주소를 열면 같은 숫자가 보인다.
6. **유지:** 다시 배포한 뒤에도 숫자가 그대로다.
7. **실패:** 허용 목록에 없는 주제를 보내면 400이고 행이 생기지 않는다.

# 기능 계획 2: 작품 응원

## 한 줄 요약

홈페이지의 작품 3개(사진·영상·그림) 중 마음에 드는 작품에 방문자가 응원을 남긴다. 응원 한 건을 한 행으로 저장하고, 작품별 누적 응원 횟수와 최근 응원 시각을 보여 준다. 숫자 하나를 읽고 덮어쓰지 않는다.

| 항목 | 결정 |
|------|------|
| 기능 이름 | 작품 응원 |
| 사용자 행동 | 작품 카드의 [응원하기] 버튼을 누른다 (자유 입력 없음, 로그인 없음) |
| 저장 데이터 | 고유 번호(`id`), 작품 번호(`work_id`), 저장 시각(`created_at`) |
| 작품 번호 | `photo-night`(야경 사진), `animation-short`(짧은 애니메이션), `poster`(포스터) |
| 작품 제목·이미지 | `index.html`에 둔다. DB에는 저장하지 않는다 |
| 배포 서비스 | Netlify (기존과 같음, 함수 `/api/cheers`) |
| 저장소 | Supabase (`cheers` 테이블, `cheer_stats` 뷰). 기존 `votes`와 별개 |
| 표현 | "누적 응원 N회". 중복 참여가 가능하므로 "방문자 N명", "1인 1표"라고 쓰지 않는다 |

예시 기록: `1 / photo-night / 2026-11-02 14:20` (고유 번호는 DB가 1, 2, 3 … 으로 매긴다)

## 화면

"03 — WORKS" 섹션, 메뉴 "작품".

- 작품 카드 3개: 자리 표시 이미지, 분류 태그, 제목, "누적 응원 N회", "최근 응원: 날짜 시각", [응원하기] 버튼
- 이미지가 생기면 `.work-thumb` 자리에 `<img>`를 넣는다

## 성공 · 실패 동작

| 상황 | 화면 | API |
|------|------|-----|
| 불러오기 성공 | 작품별 "누적 응원 N회", 최근 시각 (없으면 "아직 없음") | `GET /api/cheers` → 200 `{works}` |
| 불러오기 실패 | "응원 수를 불러오지 못했습니다." 숫자 "—" | 502·500, GitHub Pages는 404 |
| 저장 중 | "응원을 저장하는 중…" 버튼 3개 모두 꺼짐 | |
| 저장 성공 | 다시 불러온 뒤 "응원이 저장되었습니다." | `POST /api/cheers` → 201 |
| 저장 성공, 다시 불러오기 실패 | "응원이 저장되었지만 숫자를 불러오지 못했습니다." | |
| 없는 작품·빈 값·숫자·배열 | 저장하지 않음 | 400 "없는 작품입니다." |
| 요청 본문 1,024자 초과 | 저장하지 않음 | 413 |
| DB·네트워크 오류 | "응원을 저장하지 못했습니다. 잠시 후 다시 시도해 주세요." 숫자 그대로 | 502 |

## 구조와 접근 제한

```
index.html                     작품 카드와 화면 코드
netlify/functions/cheers.mjs   /api/cheers 서버 함수 (dist/ 로 복사하지 않음)
supabase/cheers.sql            cheers 테이블·cheer_stats 뷰·RLS
```

- 흐름: 브라우저 → `/api/cheers` (Netlify 함수) → Supabase REST API. 브라우저에는 키가 없다.
- 환경 변수는 기존 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`를 그대로 쓴다. 새로 넣을 값은 없다.
- 함수가 작품 번호를 허용 목록으로 먼저 검사하고, DB도 `check` 조건과 RLS로 한 번 더 막는다.
- `anon` 권한: `cheers` 읽기, `work_id` 컬럼만 쓰기. 수정·삭제 불가. 고유 번호와 시각은 방문자가 정할 수 없다.
- 집계는 DB 뷰가 `count(*)`로 하므로 응답은 작품 수(최대 3줄)다. 조회 건수 제한으로 빠지는 기록이 없다.
- IP·기기 정보는 저장하지 않는다. 같은 사람이 여러 번 누르는 것은 막지 않는다.

## 완성 검사 방법

1. **스키마:** Supabase SQL Editor에서 `supabase/cheers.sql` 실행 후 권한 검사 쿼리 결과 확인.
2. **API:** 배포 주소 `/api/cheers`가 200과 작품 3개의 `{count, last_at}`을 돌려준다.
3. **요청서 검사 예:** 사진 0회에서 내 컴퓨터로 한 번, 휴대폰으로 한 번 누른 뒤 두 화면을 새로고침하면 모두 "누적 응원 2회"다.
4. **DB 행:** Table Editor의 `cheers`에 `photo-night` 행 2개가 각자 고유 번호와 시각을 갖고 있다.
5. **거절:** 없는 작품 번호(`photo-day`)를 보내면 400이고 행이 늘지 않는다.
6. **실패 표시:** 휴대폰을 비행기 모드로 두고 누르면 실패 메시지가 나오고 숫자가 그대로다.
7. **기존 기능:** "다음 그림 주제" 투표 숫자가 전과 같다.
